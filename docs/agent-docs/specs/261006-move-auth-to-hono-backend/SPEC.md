## Overview
Robin Talks was client-only: accounts, sessions, OTP codes, and password reset went
through the Borel cloud proxy at `api.borel.one`. This feature stands up that same
auth surface inside our own Hono backend (`apps/backend`) using better-auth with a
drizzle adapter over the provided Neon Postgres database, and then moves the mobile
app onto it. The auth service, its schema and migration, and endpoint conformance
are done and verified (AC-1 through AC-14). The first update (AC-15 through AC-20)
repointed the native mobile auth client at the backend and migrated the app's own
data tables (`learner_profiles`, `practice_sessions`, `robin_memory`, and
`profiles`) to backend endpoints. This update (AC-21 through AC-29) does the same
for the browser preview: its auth client and its app data move off the Borel broker
onto the backend, so both surfaces authenticate and persist against the same Hono
service. Borel stays for file storage, AI image generation, moderation,
notifications, and the account/usage/invite links, none of which the app's screens
call (chat and speech-to-text already go straight to OpenRouter).

## User Stories
- As a Robin Talks developer, I want accounts, sessions, OTP codes, and password reset served by our own Hono backend, so auth logic and account data stop depending on the Borel proxy.
- As a learner, I want the backend to offer sign-up, email verification with a 6-digit code, sign-in and sign-out, password reset, password change, and account deletion, so the app can keep the same experience when it moves.
- As a developer, I want the auth tables created by a committed drizzle schema and migration, so the database is reproducible from the repository.
- As an operator, I want the OTP email transport to be configurable by environment, so development captures codes in-process and production sends real email without a code change.
- As a learner, I want to sign up, verify, sign in, reset my password, change it, and delete my account through our own backend, so the app no longer depends on the Borel auth proxy.
- As a learner, I want my profile, practice sessions, and Robin memory saved to and loaded from our own backend, so my practice data keeps working after auth moves.
- As a developer, I want every data row scoped to the signed-in user by the backend, so one account cannot read or write another's data.
- As a developer, I want the browser preview to sign in against the Hono backend, so the preview no longer depends on Borel's brokered session.
- As a browser-preview user, I want my profile, sessions, and Robin memory saved to and loaded from the backend, so my preview data keeps working after auth moves.
- As a developer, I want one auth and data path shared by the phone and the browser, so there is a single service to reason about and test.

## Edge Cases
- Duplicate sign-up: with `requireEmailVerification: true`, better-auth returns HTTP 200 with `token: null` and a synthetic user rather than an already-exists error, so the neon-js adapter surfaces `SessionNotFound`; `authErrorMessage`'s already-exists branch applies only when verification is not required. The test asserts the 200 generic response and that no second row is created.
- Wrong or expired verification code: `/api/auth/email-otp/verify-email` fails with an invalid-OTP error.
- Password reset requested for an unknown address: the endpoint succeeds and no code is delivered, so accounts cannot be enumerated.
- Password shorter than 8 characters: sign-up and reset fail with a password-too-short error.
- `DATABASE_URL` and all `PG*` variables absent: starting the server is a subprocess test asserting a non-zero exit and a one-line message naming the missing variable; the subprocess runs with a working directory outside the repository so Bun does not auto-load the root `.env`.
- A request with `Origin: https://evil.example`: rejected by `trustedOrigins`/CORS, asserted with an explicit `Origin` header via `app.request` (React Native sends no `Origin`, so the device path is not the test).
- Re-running `drizzle-kit migrate` on an already-migrated database: exits 0 with no pending migrations.
- Re-running the database-backed tests: each run uses a unique email and removes the user in `afterAll`, so no state carries over.
- A data request with no session or an expired session: rejected (401) and the mobile hook surfaces its plain "load"/"save" sentence, never another user's rows.
- Two signed-in users: each sees and mutates only rows whose `user_id` is their own id (`profiles` is keyed by `id`); guessing the other's row id still returns nothing for get, update, or delete; deleting all of one user's sessions or memory leaves the other's intact.
- Deleting an account: the user's `learner_profiles`, `practice_sessions`, `robin_memory`, and `profiles` rows are removed by the `ON DELETE CASCADE` foreign keys when the better-auth user is deleted.
- Upserting a profile that already exists: updates the existing row rather than inserting a second one (conflict on `user_id`, and on `id` for `profiles`).
- Browser preview reload after sign-in: the backend session cookie survives the reload, so `getSession` still returns the user and data requests stay authorized.
- Browser sign-in in the same tab: the `onAuthStateChange` subscriber registered by `context.tsx` fires from the client's own action, not only from a cross-tab broadcast, so the navigator updates.
- Browser data CORS preflight: an `OPTIONS /api/data/profile` from the preview origin returns 204 with the allow headers; a same-origin data request with no `Origin` header is unaffected.
- Browser data request while signed out or with an expired session: rejected (401) and the hook surfaces its plain "load"/"save" sentence, never another user's rows.
- Browser preview with the Borel auth env vars unset: still works; only `EXPO_PUBLIC_BACKEND_AUTH_URL` is needed for auth.
- A Borel-hosted cross-site preview pointed at a localhost backend: out of scope; a cross-site iframe needs an HTTPS backend and `SameSite=None` cookies, which this update does not provision.
- The same account used on a phone and in the browser: both read and write the same backend rows, scoped to that user.
- Existing Borel-preview accounts and rows: not migrated; browser accounts are the backend database's.
- Native unchanged: the manual cookie jar still persists the native session and data requests still replay it.

## Non-Goals
- Migrating file storage, AI image generation, moderation, or notifications off Borel. The app's screens do not call them, so they stay on Borel and their mobile modules are unchanged.
- Deploying the backend to a public host, provisioning DNS/TLS, or serving the preview cross-site (an HTTPS backend with `SameSite=None` cookies).
- Removing the Borel `db` surface (`db.storage`, `db.ai`, `db.moderation`, `db.notify`, `db.account`) or editing the Borel-managed `db.ts`.
- Migrating existing Borel accounts, sessions, or rows into the new database.
- Social or OAuth sign-in (Apple was removed in commit `3fd77d1`).
- A specific production email vendor: only the env-selectable transport seam is in scope.
