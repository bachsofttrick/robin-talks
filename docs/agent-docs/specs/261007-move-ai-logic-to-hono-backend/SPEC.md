# Spec: Move the mobile app's AI logic into the Hono backend

Status: verified (adversarial-agent, round 4: AGREE)
Request: create a new spec for: move all AI logic in the mobile app down to hono backend, with its own route `/ai`. Get your spec and plan **(not tasks)** reviewed by `adversarial-agent` until both reach an agreement before approved and proceed. No human shall be in the loop.

Overview note: the user's "route `/ai`" is interpreted as a dedicated AI router named `/ai`, mounted under the backend's existing `/api` prefix so its endpoint paths are `/api/ai/*`, exactly matching how `/api/auth` and `/api/data` are derived from `EXPO_PUBLIC_BACKEND_URL=http://localhost:3000/api` (`.env.example` line 3). The mobile client reaches it at `BACKEND_AI_URL = BACKEND_URL + "/ai"`, the same derivation pattern as `BACKEND_AUTH_URL` and `BACKEND_DATA_URL` in `apps/mobile/src/lib/core/db/config.ts`.

## Overview
Today the mobile app holds and runs the AI pipeline itself: `apps/mobile/src/lib/core/db/ai.ts` calls OpenRouter directly for chat completions (through `@openrouter/sdk`) and speech-to-text (through raw `fetch`), calls Borel for image generation and image editing, and carries the OpenRouter API key inside the client bundle (`EXPO_PUBLIC_OPENROUTER_API_KEY`). The backend (`apps/backend`) serves only auth (`/api/auth/*`) and app data (`/api/data/*`). This feature moves the AI transport down to the backend under a dedicated `/ai` router: OpenRouter chat, OpenRouter speech-to-text, and the Borel image proxy calls all happen server-side, the API key lives only in the backend environment, and the mobile app's `db.ai` becomes a thin client over the backend endpoints. Callers (`useRobin`, the Session screen) and every public type and result shape stay the same, so the learner's experience does not change.

## User Stories
- As a learner, I want Robin's replies, transcripts of my recordings, and generated pictures to keep working exactly as today, so moving AI behind the backend changes nothing I can see.
- As a developer, I want the OpenRouter API key to live only in the backend environment, so no secret sits inside the mobile bundle.
- As a developer, I want every OpenRouter and Borel AI request issued by the backend under `/api/ai`, so there is one place that owns AI transport, timeouts, retries, and error mapping.
- As a learner, I want to still be asked before anything I type, record, or photograph is shared with an AI company, so the disclosure flow (App Store Guideline 5.1.2(i)) is unchanged.
- As a signed-in user, I want the AI endpoints to reject requests without a valid session, so the backend's AI spend is not open to anonymous callers.

## Acceptance Criteria
- AC-1 (backend `/api/ai` router): `apps/backend` mounts an `aiRouter` at `/api/ai` inside `createApp()`; it serves `POST /api/ai/chat`, `POST /api/ai/transcribe`, `POST /api/ai/images/generations`, and `POST /api/ai/images/edits`. It resolves the caller from the better-auth session cookie via `auth.api.getSession({ headers })`; with no valid session, every endpoint returns `401` with body `{ "error": "You need to sign in first." }` (the exact body the data router returns in `apps/backend/src/routes/index.ts`). With a session, every endpoint returns HTTP 200 with the endpoint's result object (the same JSON shape the mobile `db.ai` resolves today), the failure carried in the result's own `error`/`status` fields; `401` is the only error status.
- AC-2 (server-side AI configuration): the backend reads `OPENROUTER_API_KEY` and `BOREL_AI_URL` from `process.env` at call time; no module throws at import when they are absent, and each endpoint returns a failure-shape result without calling its provider: `/api/ai/chat` answers `{ text: null, data: null, error: "The AI couldn't answer that right now, so please try again.", status: 0, reason: null, truncated: false, raw: null, detail: "OPENROUTER_API_KEY is not set." }`; `/api/ai/transcribe` answers `{ text: null, error: "The AI couldn't answer that right now, so please try again.", status: 0, reason: null, detail: "OPENROUTER_API_KEY is not set." }`; both image endpoints answer `{ url: null, error: "The picture couldn't be made right now, so please try again." }` for generations and `{ url: null, error: "That picture couldn't be changed right now, so please try again." }` for edits (each with `status: 0`, `reason: null`, `reused: null`; the `AiImageResult` type has no `detail` field, so the diagnosis lives only in this spec and the code's comments). `.env.example` removes the `EXPO_PUBLIC_OPENROUTER_API_KEY` line and the `EXPO_PUBLIC_BOREL_AI` line, and adds under the `# Backend (apps/backend)` section `OPENROUTER_API_KEY` and `BOREL_AI_URL`; the root `.env` gets the same treatment with the same value mapping: the new `OPENROUTER_API_KEY` carries the value `EXPO_PUBLIC_OPENROUTER_API_KEY` held, and the new `BOREL_AI_URL` carries the value `EXPO_PUBLIC_BOREL_AI` held; both removed keys disappear from both files. `apps/mobile/src/lib/core/db/config.ts` stops exporting `OPENROUTER_API_KEY` and `BOREL_AI` and instead exports `BACKEND_AI_URL` derived as `BACKEND_URL ? BACKEND_URL + "/ai" : ""`.
- AC-3 (chat endpoint): `POST /api/ai/chat` accepts `{ model, messages, temperature, max_tokens, jsonSchema }`. The model must be a member of the allowlist, defined as the set of distinct values of the client's `ai.models` map (today one distinct id: `openai/gpt-6-luna`); an unknown model answers 200 with `{ text: null, data: null, error: "The app can't use that model, so please try again.", status: 400, reason: null, truncated: false, raw: null, detail: "model \"<the submitted id>\" is not on the allowlist" }`. Schema-less behavior: messages are forwarded to OpenRouter's chat completions through `@openrouter/sdk` `chatSend` with `provider: { only: ["openai"] }`, retries off, a 60s timeout, and `image_url`/`input_audio` parts mapped to the SDK's camelCase field names; the reply's text (assistant text joined across content parts), `truncated: finishReason === "length"`, and the rest of the result follow the moved `chatOnce` code, with `data: null`. Transport failures map by the same rule the moved code used: `RequestAbortedError`, `RequestTimeoutError`, or a fetch `AbortError` answer the slow sentence (`"The AI took too long to answer, so please try again."`) with `status: 0`; `ConnectionError` or any other thrown error answers the offline sentence (`"Couldn't reach the AI, so check your connection and try again."`) with `status: 0`; OpenRouter error statuses map 402/404 to the `wallet_empty` sentence (`"AI isn't available right now, so please try again later."`), 403/429 to the `daily_allowance_used` sentence (`"AI has reached today's limit, so it's back tomorrow."`), 401/502 to the failed sentence, and anything else to the API's own words only when they already read as one plain sentence, passing the provider status through as `status`. Structured-output behavior, only when `jsonSchema` was supplied: the schema is converted to a strict `response_format` json_schema (`{ type: "json_schema", jsonSchema: { name, strict: true, schema } }`), a reply that cannot be read as JSON is asked for once more (at most 2 attempts total), a reply cut off at `max_tokens` (`truncated`) answers with the too-long sentence (`"That answer was too long, so try asking for less."`) and detail `"The answer reached max_tokens and was cut off."`, a readable reply is returned with `data` set to the parsed value, and two unreadable replies answer with the unreadable sentence (`"That answer came back in a form this app couldn't read, so please try again."`) and detail `"The answer was not valid JSON."`. Without a `jsonSchema`, there is no retry and no truncation error: `truncated: true` is returned with `error: null`. The endpoint performs no consent of its own and never calls `noteRefusal`: chat results always carry `reason: null`. The result is the `AiChatResult` object verbatim (`text`, `data`, `error`, `status`, `reason`, `truncated`, `raw`, `detail`). The endpoint ignores body fields it does not know.
- AC-4 (transcribe endpoint): `POST /api/ai/transcribe` accepts `{ audio: { data, format } }`, where `data` is the base64 or data: URL payload the client already normalized. The endpoint ignores unknown body fields; the mobile client continues to accept `{ audio, language?, prompt? }` in its public signature and sends only `{ audio: { data, format } }`, dropping `language` and `prompt` before the request. It calls OpenRouter's `/audio/transcriptions` with the pinned audio model `qwen/qwen3-asr-0.6b`, a 60s timeout, and the `format` hint (default `m4a`). Backstop guards server-side, using the same sentences the moved code used: for the cap, the `data:` prefix (through the first comma) is removed, and a base64 body longer than 4194404 characters answers `{ text: null, error: "That recording is too long to send, so try a shorter one.", status: 0, reason: null, detail: "The recording exceeded the 3 MB audio cap." }`; an empty body — the stripped string is empty after `.trim()`, exactly the `!base64Body(clip.data).trim()` predicate — answers `{ text: null, error: "No words were heard in that recording, so please try again.", status: 0, reason: null, detail: "The recording had no audio in it." }` without calling OpenRouter. The response is the `AiTranscribeResult` object verbatim (`text`, `error`, `status`, `reason`, `detail`); transport failures map exactly as in AC-3 (slow/offline sentences, `status: 0`), OpenRouter error statuses map by the AC-3 table, and a reply with no readable text answers the noSpeech sentence with detail `"The recording had no speech in it."`. The endpoint never calls `noteRefusal`: transcribe results always carry `reason: null`.
- AC-5 (image endpoints): `POST /api/ai/images/generations` accepts `{ prompt, size? }` and `POST /api/ai/images/edits` accepts `{ image, prompt, size? }` (the image already normalized by the client to an https or data URL); both ignore unknown body fields. The backend proxies each to Borel at `BOREL_AI_URL + "/images/generations"` and `"/images/edits"` with a 150s timeout, forwarding the request's `Authorization`, `X-Borel-Surface`, and `X-Borel-Build` headers verbatim (present or absent) so Borel's metering, refusal wording, and surface policy behave exactly as they do when the client calls Borel today. On failure: `reason` is the mapped refusal (`refusalOf`: `wallet_empty`, `daily_allowance_used`, or `cloud_paused`, via the same status/`reason`-field matching the moved code used) and `error` is `reason`'s neutral sentence (`"AI isn't available right now, so please try again later."` / `"AI has reached today's limit, so it's back tomorrow."` / `"This isn't available right now, so please try again later."`), otherwise `error` is Borel's own message when it already reads as one plain sentence, otherwise `"The picture couldn't be made right now, so please try again."` for generations and `"That picture couldn't be changed right now, so please try again."` for edits, with Borel's HTTP status passed through as `status`. On success: `error: null`, `status` is Borel's status, `reason: null`, and `reused` is Borel's `reused` flag (`false` or `true` when Borel sent one, `null` when it sent none); on failure `reused` is `null`. The response is the shape `{ url, error, status, reason, reused }`. Transport failures (Borel unreachable) answer the offline sentence with `status: 0`, `reason: null`, and `reused: null`; a timed-out request answers the slow picture sentence (`"The picture took too long, so please try again."`) with `status: 0`, `reason: null`, and `reused: null`, the same for both endpoints.
- AC-6 (mobile thin client): `apps/mobile/src/lib/core/db/ai.ts` keeps its public surface verbatim: `ai.chat`, `ai.transcribe`, `ai.image`, `ai.editImage`, `ai.models` (the two pinned ids), and every exported type (`ChatMessage`, `ChatContentPart`, `AiChatResult`, `AiTranscribeResult`, `AiImageResult`, `AiJsonSchema`, `AiImageAsset`, `AiImageInput`, `AiAudioRecording`, `AiAudioInput`). The implementations become calls to the backend endpoints above, and these behaviors stay client-side because only the device can do them:
  - The consent gate: `askAiConsent` runs before any backend request, with the exact same kind selection as today — chat inspects the messages and asks `withAudio ? "audio" : withPhoto ? "photoChat" : "chat"` with the chosen model, transcribe asks `"audio"` with `AI_AUDIO_MODEL`, image asks `"image"`, editImage asks `"editImage"`; a decline resolves the exact decline sentence `"This feature shares what you send with AI, so it needs your permission. Use it again and tap Allow to turn it on."` (`AI_DECLINED`) with the same failure fields as today (`status: 0`, and `reason: null`) and issues no request.
  - Device-file normalization for chat's `image_url` parts: `sendableImage` turns device uris, assets, and picker results into https or data: URLs before the request, resolving `"No photo was chosen."` when there is no photo and `"That photo couldn't be read, so try picking it again."` when reading one throws (both with `status: 0`); chat's `input_audio` parts pass through untouched; transcribe's audio normalization (`sendableAudio`, same caps, same sentences) also stays client-side.
  - The in-flight dedupe for `image()` only: one shared promise per `prompt + "|" + size` key, failures dropped so a retry is possible; `editImage()` does not dedupe, as today.
  - The browser metered post: when an image result comes back and its `reused` is not `true` (the exact predicate today's code applies, `!reused`, so a `false` and a `null` both count as a fresh picture) and `IN_BROWSER`, the client still posts `postToParent({ type: "ai:metered" })`; the client then strips `reused` and resolves the unchanged `AiImageResult` shape (`url`, `error`, `status`, `reason`).
  - The refusal record: when an image result carries a `reason`, the client still runs `noteRefusal(reason)`; chat and transcribe never do (their results carry `reason: null`).
  The client sends no API key and talks only to the backend: requests go to `BACKEND_AI_URL`, native replays the session cookie header exactly as the data client does (`Cookie` header built from `sessionCookieHeader()`, `credentials: "omit"`), the browser sends `credentials: "include"` with no `Cookie` header. Image requests carry `Content-Type: application/json` and the Borel headers exactly as `borelFetch` sends them today: `X-Borel-Surface` always (from `borelHeaders()`), `X-Borel-Build` when one exists, and `Authorization: Bearer <authHeader()>` only when `authHeader()` resolves non-empty, with the header omitted entirely when the bearer is empty. The client applies its own timeouts and maps a timeout to the slow sentence (`"The AI took too long to answer, so please try again."` for chat and transcribe, `"The picture took too long, so please try again."` for both image endpoints) and a network failure to the offline sentence, each with `status: 0` — precisely: chat, transcribe, and both image endpoints all resolve `"Couldn't reach the AI, so check your connection and try again."` (`AI_SAYS.offline`, exactly what today's code produced for a thrown or connection failure on every path), while only the timeout wording differs per surface as above. Timeouts: 65000ms for chat and transcribe (the provider's 60s plus margin) and 160000ms for both image endpoints (Borel's 150s plus margin). A 401 response resolves the body's `error` sentence when readable, otherwise `"Sign in to use this feature."`. An unset `BACKEND_AI_URL` resolves `"The backend is not configured."` with `status: 0` for every endpoint, before any request. The client never references `https://openrouter.ai` and no longer reads an OpenRouter key.
- AC-7 (callers unchanged): `useRobin` (`nextTurn`, `debrief`) and the Session screen's `db.ai.transcribe` call require zero edits, because the public surface and result shapes are unchanged; their prompt building, schemas (`TURN_SCHEMA`, `DEBRIEF_SCHEMA`), and scenario logic stay in the mobile app.
- AC-8 (CORS for the preview): `/api/ai/*` carries the same `cors({ origin: trustedOrigins(), credentials: true })` middleware as `/api/data/*`, so the browser preview's credentialed AI requests reach the handlers. With `TRUSTED_ORIGINS=http://localhost:8081` in the test environment (the app test's hermetic env helper may set it explicitly), a test asserts an `OPTIONS` preflight to `/api/ai/chat` returns 204 with `Access-Control-Allow-Origin: http://localhost:8081` and `Access-Control-Allow-Credentials: true`, and a credentialed `POST /api/ai/chat` with that `Origin` gets the same allow headers alongside the 401 body.
- AC-9 (dependencies): `apps/mobile/package.json` drops `@openrouter/sdk` and its entry in the Jest `transformIgnorePatterns` allow-list (the `zod` entry stays; it may serve other deps); `apps/backend/package.json` gains `@openrouter/sdk` pinned to the same version (`^1.4.18`); the root `bun.lock` is updated. Nothing else moves between the workspaces.
- AC-10 (tests move with the code): the OpenRouter-transport behaviors now covered by `apps/mobile/src/lib/core/db/ai.test.ts` are covered by `bun:test` suites in `apps/backend` (chat mapping, schema forwarding, retry loop, truncation, transport-failure mapping, the model allowlist, transcriptions mapping and guards, the image proxy mapping and header forwarding, the 401 gate), mocking the OpenRouter SDK (or `globalThis.fetch`) and the Borel `fetch` so no real network is needed; the AI router's session resolver is substituted with a fake in those suites so they need no database. A test asserting the real better-auth 401 gate (no cookie → 401 body of AC-1) lives with the database-backed e2e suite and skips, with a reported reason, when no database is configured. The mobile suite keeps `consent.test.ts` unchanged, replaces the transport cases in `ai.test.ts` with thin-client cases (requests hit `BACKEND_AI_URL` with the right cookie/credentials and, for images, the Borel headers; consent still gates the call; timeout/offline/401/unconfigured resolve the exact sentences of AC-6; `image()` dedupe shares one promise per key while `editImage()` does not; a refusal reason still notes the client-side refusal; the browser still posts `ai:metered` when `reused` is not `true` (the exact `!reused` predicate, so both `false` and `null`/missing count as fresh)), and passes: mobile `lint`, `typecheck`, and `test`; backend `lint`, `typecheck`, `test`, and `build`.
- AC-11 (no direct AI traffic from the app): after the move, no module under `apps/mobile/src` imports `@openrouter/sdk` (the dependency is gone, so typecheck enforces it), and an automated case-sensitive source check (part of the mobile test suite, reading the files under `apps/mobile/src`) asserts the lowercase string `openrouter.ai` appears in no mobile source file except `consent.ts`, whose wording intentionally names `OpenRouter.ai`; the only provider address otherwise left in the mobile source is Borel's non-AI surfaces (storage, account, notifications), which stay out of scope. The consent wording keeps naming OpenRouter.ai and the model makers, because the disclosure is about where the data ends up, which is unchanged.

## Edge Cases
- Learner declines the consent dialog: the mobile client resolves the decline sentence (`AI_DECLINED`, quoted in AC-6) and issues no backend request; the backend is never reached.
- No session (expired or absent): every `/api/ai` endpoint returns 401 with `{ "error": "You need to sign in first." }` and the mobile client resolves that sentence (or its fallback "Sign in to use this feature." when the body is unreadable).
- `OPENROUTER_API_KEY` unset on the backend: `/api/ai/chat` and `/api/ai/transcribe` return the exact failure shapes quoted in AC-2; no OpenRouter request is attempted.
- `BOREL_AI_URL` unset on the backend: both image endpoints return the exact failure shapes quoted in AC-2; no Borel request is attempted.
- OpenRouter unreachable or slow: the backend maps it to the offline/slow sentences with `status` 0 and `detail` of the underlying message, inside a 200 result (AC-3 rule).
- OpenRouter refusal statuses on chat/transcribe: mapped by the AC-3 table (same sentences, `reason: null`, provider status as `status`); the client records no refusal for them, matching today's code.
- Structured-output reply that is not valid JSON: asked for once more; a second unreadable reply resolves the unreadable sentence; a reply cut off at `max_tokens` resolves the too-long sentence; all only when `jsonSchema` was supplied.
- Schema-less chat reply cut off at `max_tokens`: returned with `truncated: true`, `error: null`.
- Recording larger than the cap: refused client-side before any request (same sentence); a request that still arrives oversize is refused server-side by the AC-4 backstop guard with the same sentence and no provider call.
- Recording with no audible speech, or an empty base64 body: resolves the noSpeech sentence (client guard as today; server guard per AC-4).
- A photo the device cannot read: the client resolves the unreadable-photo sentence, or `"No photo was chosen."` when there is no photo at all (both with `status: 0`), before any request.
- Two `image()` calls for the same `prompt + "|" + size` while the first is in flight: the client shares one promise (one backend request); `editImage()` never dedupes.
- Borel refusing an image request (wallet/allowance/paused): the backend maps the reason and neutral sentence (AC-5); the client's `noteRefusal` still records it for the notices UI.
- The browser preview making a fresh Borel picture: the client still posts `ai:metered` to the parent when `reused` is not `true` (the `!reused` predicate of AC-6), so a missing flag does not suppress the post.
- The app with `EXPO_PUBLIC_BACKEND_URL` unset: AI calls resolve `"The backend is not configured."` like the data client.
- A request to `/api/ai/*` from an unknown origin in the browser: no `Access-Control-Allow-Origin`, so the browser blocks it; native sends no `Origin` and is unaffected.
- The learner signs out while a request is in flight: the in-flight request completes against the still-valid session server-side; a retry after expiry resolves the sign-in sentence.

## Non-Goals
- Moving Robin's prompt construction, the turn/debrief schemas, or the scenario orchestration into the backend. `/api/ai/chat` is a general structured chat endpoint; the app-domain "what to ask" stays in the mobile app.
- Streaming responses: the backend answers with one complete result, as today.
- Moving consent to the backend or storing consent server-side: consent is a device UI and storage concern and stays in the mobile app.
- Moving file storage, moderation reports, notifications, or the account/usage/invite links off Borel: untouched Borel surfaces.
- Changing model ids, prompts, wording, retry counts, or timeouts beyond what relocation requires.
- Per-user AI metering, rate limiting, or cost accounting on the backend.
- Deploying the backend anywhere or touching the hosted preview setup beyond the existing local one.
